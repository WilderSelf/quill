# 0079 — A book: several chapters, one press file

**Milestone:** M6 · **Status:** implemented

## Why

A 500-page game book or a textbook is not authored in one file. It is authored as chapters, by
different people, on different days, and it has to come out of the far end as **one** press-ready
PDF: one page-number sequence, one contents list, one set of embedded font subsets, one
OutputIntent, one preflight.

Quill could do everything a chapter needs and nothing a book needs. `export`, `AppState`,
`OpenedTpub` and `LayoutSession` each assume exactly one `Document`, and the M6 audit named this
increment as the one that meets all four at once. It is last in the milestone because it is a
composition over everything before it: the section (0072) is what a chapter *is*, the folio (0073)
is what continuous pagination *is*, the contents list (0041/0070/0075) is what a book's front matter
*is*, and the `.qpack` (0055–0057) is the sharing mechanism that already exists and must not be
reinvented.

## The decision this spec is really about

**A book is a new artifact, and `Document` does not grow a chapter list.**

The alternative — a `chapters: Vec<...>` on `Document` — was rejected on three grounds, in
increasing order of weight:

1. It changes what `document.json` *is*. The exported `/ID` is a hash of the manifest text, so
   anything that changes what a document serializes moves every exported byte of every document.
   (An `Vec` field with `skip_serializing_if` would not, today — but the field would then be a
   permanent invitation to add the one that does.)
2. It makes `Document` recursive in meaning if not in type: every consumer of `Document` acquires a
   standing question — *am I the whole book, or a chapter of one?* — that it can only answer by
   convention. That is a one-way door, and it is the door the four one-`Document` call sites would
   have to walk through.
3. It gets the layering backwards. A chapter does not know it is in a book; a book knows what its
   chapters are. Putting the list on `Document` would mean a chapter opened on its own carries a
   claim about a file it does not contain.

**And the book resolves to one `Document` before it reaches the engine.** This is the second half of
the decision and it is what makes the increment shippable. `Book::compose` is a pure function from a
book manifest plus its chapters' documents to **one** `Document` — content concatenated, block ids
rebased, assets namespaced, styles merged, one `Section` synthesised per chapter. Everything
downstream is then unchanged, and *that is the argument*: the layout fixpoint, the incremental
session, the font-subset collector, geometry preflight, the PDF/X writer and the outline are the
ones that have been tested against every increment since M0. Teaching four crates a second
N-document code path would give the press file a route that nothing else in the repository exercises,
and press output is the reason the product exists.

It also means the cost is not hidden. Composing does not make a book cheaper than N chapters — the
audit's arithmetic (iterations × chapters) is identical either way, expressed as passes over one
long document rather than as passes over N short ones. What it does is put that cost on the code
path the perf harness already measures. See *Performance* below, which measures it.

## What

### The book file

A **book file** is plain JSON with the extension `.qbook` — not a container, for the reason a
template file (spec 0053) is not one: a book links no assets of its own. Its chapters are `.tpub`
containers and they carry theirs.

```json
{
  "book_version": 1,
  "metadata": { "title": "The Ruined Keep", "authors": ["A. Cartographer"] },
  "requires": [ { "name": "house-style", "version": "1" } ],
  "chapters": [
    { "path": "front.tpub", "name": "Front matter",
      "folio": { "format": "lower_roman", "restart_at": 1 } },
    { "path": "ch1.tpub", "name": "The Ruined Keep",
      "folio": { "format": "decimal", "restart_at": 1 } },
    { "path": "ch2.tpub", "name": "The Sunken Vault" }
  ]
}
```

- `path` is relative to the book file, and is refused if it is absolute or escapes the book's
  directory — `safe_relative_path`, the same rule a `.tpub` entry and a `.qpack` path already get.
- `name` is the chapter's name **as a section**: it is what `{section}` prints in a running head and
  what the chapter's synthesised `Section` is called.
- `folio` is exactly spec 0073's `Folio`, and `restart_at`'s doc comment already said this is where
  it would be read: *"`Some(n)` is the offset a chapter extracted from a larger book needs."*
- `master` names the master applied to the chapter's opening page. Omitted, the chapter's own
  positional override for its own page 0 supplies it (see below).
- `requires` is spec 0056's list, unchanged. **Shared styles are `.qpack` and nothing else.** The
  book's requirements and its chapters' are unioned onto the composed document, and a requirement
  that does not resolve is a refusal, not a fallback — 0056's posture, inherited rather than
  restated.

### `BOOK_VERSION`, and the fourth version gate

`BOOK_VERSION` is **1**. `migrate_book` is written beside `migrate_template` and `migrate_pack` arm
for arm, because `version.rs` already says why: *"a third differently-shaped version gate would be a
third thing to get wrong."* A fourth is worse. Same three steps — read the declared version, refuse
a newer one, stamp the current one — same empty chain, same two error variants
(`BookParse`, `UnsupportedBookVersion`).

**`FORMAT_VERSION` stays 9.** The rule in `docs/format-spec.md` turns on what an *older build*
does with a *document*, and this increment adds no field to `Document`, `StyleSheet`, `MasterPage`,
`PageSetup` or `PageOverride`. A build that predates books, handed a `.qbook`, does not recognise the
extension and never opens it — neither half of the rule fires, because there is no silence to be
wrong in and nothing of the author's to lose. `TEMPLATE_VERSION` and `PACK_VERSION` stay 1 for the
same reason.

### Composition, in order

`Book::compose(&self, chapters: &[Document]) -> Result<ComposedBook, LoadError>` is pure: no
filesystem, no packs, no layout. `Book::open_into` is the half that touches the disk.

1. **Page setup.** `trim`, `bleed_pt` and `facing_pages` must be equal across chapters or the book is
   **refused**. These are the three a mixed value corrupts: a press file whose pages are not one trim
   is not a press file, and POD will reject it. The other `PageSetup` fields — margins, baseline grid
   — are taken from chapter 0 and a difference is *reported*, because those are design decisions the
   book is entitled to settle and a printer is not harmed by either answer.
2. **Block ids are rebased.** Chapter *i*'s ids are shifted by the running maximum of the chapters
   before it, so the composed document has no collision. Every id-carrying site moves by the same
   offset — the block's own id, a `Section::start`, a `RunSource::Reference`'s target, a
   `RunSource::Footnote`'s note, a `Footnote`'s own id — which is what makes a chapter's internal
   references still mean what they meant. The remap goes through `RunSource::remap`, an **exhaustive
   match**, so a future `RunSource` variant carrying an identity does not compile until it is
   handled: 0074's structural treatment, at the one site in this increment that owes it.
3. **Assets are namespaced.** Chapter *i*'s asset ids become `i/<id>` and its asset paths become
   `chapters/<i>/<path>`; `Block::Image` and `MasterStatic::Image` references are rewritten with
   them. Two chapters that both link `assets/map.png` under the id `map` are the ordinary case, not
   an error, and namespacing is unconditional so there is one path rather than a
   collision-detecting one.
4. **One `Section` per chapter is synthesised**, anchored to the chapter's first block, named from
   the book, carrying the book's `folio` and master. It is appended **after** that chapter's own
   sections, so where the two land on the same page the book wins — the existing "later authored
   wins" tie-break (spec 0072), used deliberately: a chapter that restarts its own numbering on its
   own first page would print a second page 1 inside a book.
5. **Positional page overrides.** A chapter's override for its own page 0 becomes the synthesised
   section's master, because "the chapter's opening page" is exactly what a section anchor expresses
   — which is spec 0072's finding, that index assignment is the right representation and the wrong
   authoring surface. Overrides for a chapter's *later* pages are **dropped and reported**: they name
   positions in a document that no longer starts at page 1, and the offset they would need is
   derived, not known. This is why the bundled templates' chapter openers survive composition.
6. **Styles, masters and component definitions merge first-wins**, and a *differing* definition of a
   name already taken is reported. Identical redefinitions — which is what every chapter built from
   one template has — are silent, because reporting them would bury the one that matters.
7. **Footnotes concatenate**, and their numbering is therefore book-sequential. That is 0077's
   document-sequential rule at book scale rather than a new one; a per-chapter restart is the same
   shape 0077 already rejected.
8. `assign_missing_block_ids` runs last, so the composed document is validated for duplicate ids by
   the check that has always done it.

### What composition does *not* change

**Numbering does not move the flow.** Folios, running heads and section names are furniture and
consume no flow space (`LaidOutPage::statics`), so making a chapter's pages count from 187 rather
than from 1 cannot move a line break. What *can* move one is named rather than left implicit: the
book's contents list, a cross-reference whose folio grew a digit, a pack style the chapter did not
define, and the opener master arriving on a page that is no longer the chapter's page 0. Each is a
real change to what is set, and each is supposed to move it.

### Continuous pagination

There is no page-number offset anywhere, and that is the point.

The composed document is one page vector, so the default numbering — the `FolioRun` at page 0,
arabic from 1, which spec 0073 guarantees always exists — already runs continuously across every
chapter. Chapter 2's first page carries the number chapter 1's last page implies, with nothing
stated by anyone.

A book that *wants* a break says so per chapter, and that statement is a `Section` with a `Folio`:
roman front matter, then a body chapter with `restart_at: 1`. This is the hook 0073 left, read
exactly as its doc comment described.

**This is also the answer to the staleness question.** The brief for this increment observed that a
page-number offset is an input to `{page}`, so it must live in `context_fingerprint` or the whole
book goes stale in the folio — the defect shape 0075 and 0077 both found. Here the offset *is* a
`Section` on the composed document, and `doc.sections` has been in `context_fingerprint` since spec
0072. A session cannot serve a stale folio because the thing that decides the folio is already
hashed. The alternative design — a `BookTemplate` wrapping `DocumentTemplate` with an offset field —
would have put the offset on the template, where `derived_fingerprint` returns `0` for a document
with no sections, and would have had to grow a new fingerprint term to be correct. Not adding the
term is worth more than the code it would have taken.

### The book's contents list

A `Block::Toc` in the front-matter chapter names headings from chapters it does not contain. It
works with no new mechanism, because after composition it *is* in the same document as them, and
spec 0041's rule still governs: derived from the final page vector on every pass, never accumulated.
A book-level `Block::Index` works for the same reason and gets the same guarantee, including 0078's
rule that ranges coalesce folios rather than page indices, so a range never spans a numbering change.

### A cross-reference into another chapter

**It is not expressible, and composition makes that structural rather than hazardous.**

A `.tpub` names a cross-reference target by `BlockId`, and a `BlockId` is unique *within a document*.
Chapter 1's block 12 and chapter 3's block 12 are both block 12. Building a book-wide reference map
over unrebased ids would resolve chapter 1's reference against chapter 3's block whenever they
collide — a wrong page number in a press file, silently, which is the failure `CLAUDE.md` forbids
above all others.

Rebasing removes the hazard by construction: a chapter's ids and its references to them shift by the
same offset, so a reference always resolves to the block it always meant, and there is no id an
author could have written in a standalone chapter that would reach into another. What a
same-chapter reference *gains* from the book is the right number: "see page 42" set on its own
becomes "see page 187" when the chapter is bound in, because `reference_folios` reads the composed
template's folio. That is asserted.

Genuine cross-chapter references are a **non-goal**, named with their path: they need a qualified
target (`{chapter, block}`) in the `.tpub` schema, which is a `BlockId` one-way door and a
`FORMAT_VERSION` bump of its own. A reference to a block the composed document does not hold prints
`[?]` — 0076's answer for an unplaced target, unchanged.

### Export

`export_book` is `export`, on the composed document. One OutputIntent, one set of subsets built by
the collector from one document's used characters, one preflight over the whole page vector. **A
book's fonts covering every chapter is not a new path to the collector** and therefore owes 0074's
structural treatment nothing: the collector walks one `Document` that contains every chapter's
content, every chapter's masters and every chapter's folio formats. That is a *result* of the
composition decision rather than a claim, and it is asserted with a character that appears only in
the last chapter.

## Acceptance criteria

1. Two chapters compose into one PDF with continuous folios: chapter 2's first page carries the
   number chapter 1's last page implies.
2. A book-level contents list in the front matter names headings from both chapters, with the
   folios those headings actually landed on.
3. A style neither chapter defines resolves from a `.qpack` across both chapters; a requirement that
   does not resolve refuses the book.
4. Roman front matter followed by a body chapter with `restart_at: 1` numbers as stated, and the
   contents list prints the same numbers the pages do.
5. Block ids are rebased so no two chapters collide, and a chapter's own cross-reference resolves to
   its target's **book** page.
6. Two chapters carrying the same asset id both place their own image.
7. `trim`/`bleed`/`facing_pages` disagreement refuses the book; other page-setup differences are
   reported, not silent.
8. A book file declaring a newer `book_version` is refused.
9. A single-document export is **byte-identical** to before this increment — `SAMPLE_EXPORT_DIGEST`
   unmoved, asserted rather than assumed.
10. The multi-chapter fixpoint is measured, budgeted, and shown to be linear in book size.

## Non-goals

- **A chapter starting on a new page — the increment's principal residual.** The model has no
  forced page break anywhere, which specs 0072 and 0073 each named as a non-goal when they met it,
  and this is the third sighting. A composed book therefore numbers continuously and correctly, its
  contents list sends a reader to the right page, and chapter 2 nevertheless begins halfway down the
  page chapter 1 ended on — which also means a chapter-opener master is applied to a page still
  carrying the previous chapter's tail. Fixing it is a **flow-loop** change of spec 0077's risk
  class, touching `FlowState`, the checkpoint/resume contract, fragmentation and the `frame_empty`
  guard at once, and it is the same mechanism "start this section on the next recto" needs — one
  increment serving three recorded requests rather than a patch for this one. Recorded in the
  roadmap's known issues rather than half-built.
- **Cross-chapter cross-references.** Argued above; the path is a qualified target.
- **A per-chapter incremental session.** The composed document goes through one `LayoutSession`,
  which is *more* incremental than N sessions would be — an edit in chapter 5 resumes from chapter
  5's checkpoint and reuses every page before it. What is genuinely lost is the ability to keep a
  chapter's measurement cache warm while a *different* chapter is being composed, which nothing asks
  for yet.
- **Editing a book in the app.** `AppState::open_book` composes and opens the result read-only-ish,
  exactly as `open` does for a `.tpub`; writing a chapter back out of a composed book would have to
  un-rebase every id, which is a save path and not a load path.
- **A per-chapter page-count report before layout.** A chapter's page count is derived, so it is
  known after the fixpoint and not before.
- **Chapters of differing trim.** Refused, above.

## Performance

`layout.fixpoint_iterations` (spec 0076) exists so this increment measures rather than discovers.
It is joined by **`layout.book_fixpoint_iterations`** and **`layout.book_scaling_ratio`**, over a
book built by splitting the synthetic document into chapters and putting a contents list in the
first.

The audit's worry was that a book's contents list makes the fixpoint span documents, so each
iteration re-lays every chapter — up to `FIXPOINT_MAX_ITERATIONS` × N chapter layouts, i.e. 80 for a
ten-chapter book. Since a pass is a whole-book pass either way, the question that actually decides
linear against quadratic is **whether the iteration count grows with the chapter count**, so the
workload holds the total content fixed at ~200 pages and varies only how many chapters it is cut
into.

**Measured: 3 iterations at five chapters and 3 at ten — `book_chapter_ratio` = 1.0.** The cost is
`iterations × book`, not `iterations × chapters × book`: linear in the book's page count and
indifferent to how many files it was authored in. Both counters are checked with `check_exact`,
including the ratio, because both sides are deterministic pass counts and the 2.0 tolerance would
put the ratio's limit on 3.0 — well past the 2.0 a cost that multiplied by chapter count would
read, which is spec 0051's unreachable-limit trap. `book_ms_per_page` catches the case those two
cannot: the same number of passes, each doing more work.
